# Session 思考时间展示设计

**日期：** 2026-08-13  
**状态：** 已确认，待实施计划  
**范围：** Theme V2 普通聊天与闪念 Session 的结构化处理计时

## 目标

在普通聊天和闪念的共用 Session 界面中增加一致的思考时间反馈：处理过程中实时走秒，处理完成后保留服务端记录的最终耗时。计时必须表达结构化处理耗时，而不是网络上传、录音或语音转写的总耗时。

## 已确认的产品决策

- 普通聊天和闪念都显示实时思考计时与完成后的最终耗时。
- 闪念只从进入 `agent_processing`（界面为“正在整理”）开始计时，不包含录音、上传和转写。
- 采用“处理卡右侧实时计时 + 助手回复底部最终耗时”的布局。
- 实时格式为计时器格式：小于一小时使用 `mm:ss`，一小时及以上使用 `h:mm:ss`。
- 完成态使用自然语言，例如 `思考 8 秒`、`思考 1 分 8 秒`。
- 实时反馈由客户端秒表负责；最终值以服务端 `elapsed_ms` 为准。
- 不在该位置展示 token 数。

## 现有能力

普通聊天和闪念已经共用 `ThemeV2SessionPage`、`SessionTranscript` 与 `ChatMessage`。`ChatMessage` 已包含 `elapsedMs`，普通聊天的 `done` SSE 事件和历史 Session 消息也已经携带 `elapsed_ms`。当前缺口是：

1. 消息没有可用于恢复实时秒表的结构化处理开始时刻。
2. `SessionAnalysisBlock` 只显示“处理中”，没有展示动态耗时。
3. 完成后的助手消息没有消费 `elapsedMs`。
4. 硬件闪念的 agent 消息完成时尚未持久化结构化处理阶段的 `elapsed_ms`。
5. 闪念必须在转写与结构化处理之间建立明确的计时边界。

## 架构

### 消息计时状态

为助手 `ChatMessage` 增加一个可空的结构化处理开始时刻。该字段只描述客户端实时展示状态；现有 `elapsedMs` 继续描述服务端最终耗时。

- `processingStartedAt != null && streaming == true`：显示实时秒表。
- `elapsedMs != null && streaming == false`：显示最终思考耗时。
- 两者都为空：不显示思考时间。
- `elapsedMs` 一旦到达，始终优先于本地估算值。

开始时刻存放在消息模型上，而不是页面 State 中，因此列表重建、键盘变化或轻量导航刷新不会让秒表归零。

### 普通聊天计时起点

用户发送有效消息并创建本地助手占位消息时，立即记录结构化处理开始时刻。此后“正在理解”“检索 / 执行”“组织回答”等阶段共享同一个连续秒表。收到 `done` 后保存 `elapsed_ms` 并停止实时展示。

### 闪念计时起点

录音、接收和转写继续使用现有 transient capture 状态，不创建思考秒表。只有 capture activity 进入 `agent_processing` 对应的 organizing 状态时，才为相应的运行中助手消息设置结构化处理开始时刻。

若运行中的闪念消息由后台刷新恢复：

- 有可用的 agent-processing activity 时间时，以该时间恢复秒表。
- 没有可靠起点时，从客户端观察到结构化处理状态的时刻开始，避免错误地把转写时间计入。

### 闪念最终耗时

capture process job 在 `_prepare_capture_processing` 将状态切换为 `agent_processing` 后启动单调时钟，并在 agent provider 成功或失败时停止计时。该区间只覆盖结构化理解、工具执行与结果组织，不包含录音、上传、排队和 ASR。

最终毫秒数持久化到物化闪念 Session 的 agent `SessionMessage.elapsed_ms`。成功与失败路径都必须写入；Session invalidation 触发客户端刷新后，完成态直接使用该服务端值。用于同步等待接口的整体 `elapsed_ms` 不得作为闪念思考时间，因为它可能包含转写等待。

### 完成与历史恢复

普通聊天收到 `done.elapsed_ms` 后，控制器写入 `ChatMessage.elapsedMs`。闪念在 Session invalidation 后从已更新的 agent 消息取得 `elapsed_ms`。两类历史消息都从服务端消息恢复最终耗时，不重新启动本地秒表。

若最终服务端耗时和当前客户端计时存在差异，完成态直接切换到服务端值，不做逐帧补偿；这样最终数据保持权威，也不会延迟回复完成状态。

## 组件设计

### 实时状态

`SessionAnalysisBlock` 接收结构化处理开始时刻，并在卡片右侧显示等宽计时：

```text
[思考球]  正在理解                         00:08
           结构化处理中
```

计时器由独立的小组件局部刷新，每秒只重建时间文本，不触发整个 transcript 或 controller 的每秒通知。

### 完成状态

成功完成的助手回复在正文和卡片内容之后增加轻量元信息行：

```text
联系人已创建……
────────────────
◌ 思考 8 秒
```

最终耗时不参与正文复制，不影响卡片操作，也不与 token 信息并列。

### 失败状态

处理失败时停止本地秒表。若服务端提供最终 `elapsed_ms`，失败提示显示 `处理 N 秒后未完成`；若没有最终耗时，则保持现有失败文案，不展示猜测值。

### 时间格式

实时格式：

- 8 秒：`00:08`
- 1 分 8 秒：`01:08`
- 1 小时 2 分 8 秒：`1:02:08`

完成格式：

- 0–999 毫秒：`思考不足 1 秒`
- 8 秒：`思考 8 秒`
- 1 分 8 秒：`思考 1 分 8 秒`
- 1 小时 2 分 8 秒：`思考 1 小时 2 分 8 秒`

耗时输入统一钳制为非负数；缺失值不展示。

## 无障碍与动效

- 处理阶段名称继续作为 live region，在阶段变化时播报。
- 秒表文本不作为每秒 live announcement，避免读屏持续打断用户。
- 完成态元信息包含可读的自然语言语义。
- 计时与 reduced-motion 无关；关闭动效时仍正常更新文本，但思考球遵循现有动效策略。

## 错误和生命周期处理

- 页面或消息组件销毁时取消本地 timer，防止残留回调。
- 同一个助手消息只能拥有一个实时 timer。
- 重试会创建新的处理周期，不复用上一次失败的开始时刻或最终耗时。
- 收到重复 `done` 时保持相同最终值，不重新启动计时。
- 转写状态变化不得创建或推进思考秒表。

## 测试策略

### 纯函数测试

- 实时格式覆盖 0、8、59、60、68、3599、3600 秒边界。
- 完成格式覆盖不足一秒、秒、分钟和小时。
- 负值被钳制，空值不展示。

### 控制器测试

- 普通聊天创建助手占位消息时设置开始时刻。
- `done.elapsed_ms` 保存最终值并结束实时状态。
- 闪念在 listening、receiving、transcribing 阶段不设置开始时刻。
- 闪念进入 agent-processing/organizing 后才设置开始时刻。
- 历史消息从 `elapsed_ms` 恢复最终耗时。
- 重试不会继承上一次计时状态。

### 服务端测试

- capture agent 成功时只测量结构化执行阶段，并写入 agent `SessionMessage.elapsed_ms`。
- capture agent 失败时仍写入已消耗的结构化处理时间。
- ASR、上传和同步等待接口耗时不会进入闪念 agent 消息的 `elapsed_ms`。

### Widget 测试

- 使用可控时钟验证 `00:00` 到 `00:01` 的局部更新。
- 运行中卡片右侧显示实时计时。
- 完成后移除实时计时，并在回复底部显示服务端最终耗时。
- 失败态有最终耗时时显示 `处理 N 秒后未完成`。
- 读屏语义不会因每秒计时更新而成为 live announcement。

### 回归测试

- 聊天文本、工具调用、结构化卡片和沉淀操作保持原有顺序。
- 闪念转写提示和 capture activity 顶栏保持原有行为。
- Session 历史恢复、滚动跟随、键盘与 reduced-motion 测试继续通过。

## 非目标

- 不增加服务端每秒 SSE 心跳。
- 不计算或展示录音、上传、转写的总耗时。
- 不展示 token、模型名或内部推理内容。
- 不修改 report 生成流程的阶段计时。
- 不为旧的、没有 `elapsed_ms` 的完成消息推算耗时。

## 验收标准

1. 普通聊天发送后，处理卡右侧从 `00:00` 实时递增。
2. 闪念转写期间无思考计时；进入“正在整理”后才从 `00:00` 开始。
3. 成功完成后实时计时消失，回复底部显示服务端最终思考耗时。
4. 重新打开包含 `elapsed_ms` 的历史聊天或闪念时，最终耗时仍可见且不重新走秒。
5. 失败、重试、页面重建和重复完成事件不会产生多重 timer 或错误累计。
