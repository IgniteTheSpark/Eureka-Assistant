## 1. 背景

UReka 已经具备较强的低成本记录能力：

```text
用户通过硬件或 App 表达
→ Agent 识别并创建结构化记录
→ 资产、Skill、日程、待办和报告持续积累
```

当前缺口不在“能不能记下来”，而在记录之后：

- 用户无法把某类记录明确转成一个可管理、可追踪的长期承诺。
- 系统可以推断节律并提醒，但推断过程对用户不可见，也缺少确认、调整和暂停。
- “习惯”和“目标”概念重叠，容易形成两套配置、两套进度和两套页面。
- 主动提醒、积累总结、报告、会前准备等能力各自生长，缺少统一候选、排序、分发和回溯模型。
- Reka 气泡、App 内通知和未来的系统通知职责容易重叠。

本稿把记录后的闭环定义为：

```text
记录
→ 形成可衡量数据
→ Reka 发现机会，或用户主动提出
→ 用户确认 Goal
→ 系统自动计算进度
→ 在合适时机提醒和反馈
→ 周期复盘
→ 继续、调整或结束
```

同时把所有主动能力统一为：

```text
候选生成
→ 激活
→ 排序与打扰控制
→ 分发
→ 用户处理
→ 结果回流
```

## 2. 产品原则

### 2.1 Goal 是承诺，习惯是结果

- **Goal**：用户对未来的明确意图，例如“每周跑步至少 3 次”。
- **习惯**：系统基于多个周期的真实行为，对稳定规律作出的描述，例如“已经连续 6 周保持每周跑步 3 次”。

用户创建和管理 Goal，不创建一套并列的“习惯对象”。

习惯作为 Goal 的派生状态：

```text
刚开始
→ 正在形成
→ 稳定保持
→ 暂时中断
→ 重新恢复
```

Goal 面向未来，有本周期是否达标；习惯根据历史形成，没有道德化的“失败”，只描述规律增强、减弱或恢复。

### 2.2 只支持可由记录自动计算的 Goal

Goal 必须绑定已有 Skill、资产类型或明确的记录集合。第一阶段不支持“成为更好的人”“提高工作能力”等无法从记录可靠计算的自由目标。

允许 AI 理解自然语言，但最终规则必须转换为用户可检查的确定性表达：

> 每周至少记录 3 次跑步训练。每周一重新计算。

### 2.3 Reka 建议，用户确认

Reka 可以发现 Goal 候选，但不能静默替用户建立承诺。

每条建议必须提供：

- 建议内容。
- 建议原因和使用的数据范围。
- 明确的计算规则。
- `设为目标`、`调整`、`暂不`、`不再建议此类目标`。

### 2.4 统计决定事实，LLM 负责理解与表达

- 进度、节律、阈值、触发时机和候选去重必须尽量确定性计算。
- LLM 可以把用户表达转换成规则、选择领域模板、生成自然文案和报告。
- LLM 不得编造不存在的规律、完成记录或目标进度。

### 2.5 主动服务是邀请，不是命令

- 不使用愧疚、责备、恐吓或攀比文案。
- 用户始终可以调整、暂停、忽略、退订。
- 忽略会降低类似内容的频率，不应导致更强催促。
- 重要结论必须可以回看来源。

## 3. 通用 Goal 模型

### 3.1 Goal DSL

任意 Goal 归一为：

```text
记录来源
+ 筛选条件
+ 衡量指标
+ 聚合方式
+ 目标方向与目标值
+ 计算周期
+ 生效范围
```

概念结构：

```yaml
source:
  skill_id: string
  asset_type: optional
  filters: []
metric:
  operator: count | sum | average | distinct_days | condition_rate | streak
  field: optional
target:
  comparator: gte | lte | between
  value: number
  upper_value: optional
period:
  cadence: daily | weekly | monthly | rolling | custom
  timezone: user_timezone
schedule:
  start_at: datetime
  end_at: optional
reminder_policy:
  mode: smart | fixed | off
state:
  status: draft | active | paused | completed | archived
```

这不是最终数据库 schema，而是产品和工程共享的计算契约。

### 3.2 通用计算能力

首版底层应支持：

| 计算 | 含义 | 示例 |
|---|---|---|
| `count` | 符合条件的记录数 | 每周跑步至少 3 次 |
| `sum(field)` | 数值字段累计 | 每月跑步 50 km |
| `average(field)` | 周期内字段均值 | 每周平均睡眠不少于 7 小时 |
| `distinct_days` | 有有效记录的不同日期数 | 每周记录亲子活动 4 天 |
| `condition_rate` | 满足条件的记录比例 | 每月 80% 的学习记录达到 30 分钟 |
| `streak` | 连续周期或连续日期达标 | 连续记录睡眠 14 天 |

目标方向支持：

- 至少达到：`gte`
- 不超过：`lte`
- 保持在区间内：`between`

### 3.3 Skill 的可衡量能力

Goal 不能依赖少量硬编码品类。每个系统 Skill 和自定义 Skill 都需要提供或生成一份 `goal_capabilities`：

```yaml
countable: true
metrics:
  - key: occurrences
    operator: count
  - key: distance
    field: distance
    operators: [sum, average]
    unit: km
  - key: duration
    field: duration
    operators: [sum, average]
    unit: minute
periods: [weekly, monthly]
templates:
  - 每周记录 {target} 次
  - 每月累计 {target} km
```

规则：

- 所有可形成多条记录的 Skill 至少支持 `count` 和 `distinct_days`。
- 结构化数值字段可以声明 `sum`、`average`、单位、有效范围和展示格式。
- 自定义 Skill 创建或更新时，同步生成候选能力；用户确认 Goal 时展示最终规则。
- 字段缺失、单位冲突或记录不可比较时，不得强行生成数值 Goal。

代表性品类可以作为验收样本，但不能成为系统能力边界。

### 3.4 Goal 创建入口

支持三个入口：

1. **从 Skill 或记录集合创建**：用户先选定数据来源，再选择适用模板。
2. **从 Goal 管理容器创建**：用户选择记录来源，系统只展示该来源可计算的模板。
3. **从 Reka 建议创建**：系统预填来源、指标、目标值和周期，用户确认或修改。

创建流程应尽量短：

```text
选择目标模板
→ 确认目标值、周期和提醒方式
→ 预览明确规则
→ 激活
```

高级项折叠：

- 开始和结束时间。
- 固定提醒时间。
- 记录筛选条件。
- 是否允许补录。
- 暂停周期。

### 3.5 Goal 管理容器

> 本节早期设想已被 [Goal Core §7.3](design-goal-core.md) 取代。

当前真值：

- `My Goals` 从资产库一级入口进入，不新增底部导航。
- 当前 Goal 使用纵向卡片墙；`active / scheduled` 分组，组内按创建时间倒序。
- 历史 Goal 使用独立历史页。
- 支持 Skill / Goal Type / Status 筛选。
- 首版无暂停、待确认列表、规则编辑或固定提醒。
- Theme V2 Home 已接入 Goals Layer；Goal 摘要、下一结算节点、当前 Goal 概览和历史入口以 [Goal Core §16.8](design-goal-core.md) 为准。

## 4. Goal 进度、习惯与周期复盘

### 4.1 进度计算

- 新记录创建、更新、删除或改类后，增量重算受影响的 Goal。
- 每个周期结束时生成不可变的周期快照，保留当时目标值、实际值和是否达标。
- 补录可以更新当前周期；历史周期是否允许回算由 Goal 策略决定，并明确展示。
- 进度必须能追溯到原始记录。

### 4.2 习惯识别

习惯判断基于多个周期的达标率、稳定性和持续时间，不单独要求用户配置。

示例：

```text
Goal：每周跑步至少 3 次
本周：2 / 3
历史：最近 6 周有 5 周达标
习惯状态：正在形成稳定规律
```

具体阈值应按周期长度和领域配置，不在本稿写死。产品文案只描述证据，不夸大因果。

### 4.3 周期结束

周期结束后生成简短复盘：

- 本周期是否达标。
- 与前几个周期相比的变化。
- 哪些记录贡献了进度。
- 下一周期是否继续。
- 是否调整目标值或提醒策略。

有限 Goal 到期后提供：

- 结束并归档。
- 按原规则继续。
- 调整后开启下一阶段。

## 5. Goal 提醒

### 5.1 提醒模式

用户确认 Goal 时选择：

- **智能提醒**：默认，由节律、进度风险和剩余机会共同决定。
- **固定提醒**：用户指定时间。
- **关闭提醒**：只计算和展示进度。

### 5.2 智能提醒类型

| 类型 | 触发含义 |
|---|---|
| 机会提醒 | 当前进入用户通常执行该行为的时间 |
| 风险提醒 | 当前进度落后，剩余合理机会开始不足 |
| 最后窗口 | 本周期仍可完成，但已接近最后合理时段 |
| 达成反馈 | 本周期目标完成或达到长期里程碑 |

示例：

```text
本周目标：跑步 3 次
当前进度：1 / 3
当前时间：周五
剩余合理机会：周六、周日
→ 进入风险提醒候选
```

### 5.3 抑制规则

出现以下情况时不再提醒或降低优先级：

- 本周期已经达标。
- 用户暂停本周期或整个 Goal。
- 用户已安排对应日程。
- 最近刚产生相关记录。
- 用户选择稍后提醒。
- 当前处于免打扰时间。
- 同类提醒仍未处理，且在冷却期内。

## 6. Reka 主动服务域

Goal 只是主动服务的一部分。候选生成器分为四个领域。

### 6.1 承诺与行动

- 新 Goal 候选。
- Goal 机会、风险、最后窗口和达成。
- 待办逾期。
- 日程临近。
- 已确认事项长期未推进。
- 用户明确设置的提醒。

### 6.2 洞察与升华

- 多条随记形成主题后的升华总结。
- 某个 Skill 或领域达到可分析数据量。
- 周报、月报和阶段报告准备完成。
- 行为趋势、异常变化或值得关注的关联。
- 一段经历可以整理成纪要、文章或回顾。

报告不能只按固定记录条数触发。每个领域需要 `report_readiness`：

```yaml
minimum_samples: number
minimum_span: duration
novelty_since_last_report: number
cooldown: duration
required_fields: []
```

判断至少考虑：

- 样本是否足够。
- 时间跨度是否足够。
- 相比上次报告是否有新信息。
- 用户是否已经查看或拒绝类似内容。
- 生成成本与预期价值是否匹配。

### 6.3 准备与预判

- 会前简报。
- 出行前准备。
- 截止日期前资料整理。
- 复诊前记录摘要。
- 与某人见面前的历史上下文。
- 新周期开始前的准备建议。

#### 会前简报

会前简报流程：

```text
扫描未来日程
→ 判断事件是否值得准备
→ 检索参与人、项目、历史会议、待办和相关记录
→ 生成带来源的简报
→ 到达 activate_at 后进入主动队列
→ 会议结束后失效
```

简报可以包含：

- 会议背景和目标。
- 历史讨论、决定和未完成行动项。
- 参与者相关信息。
- 推荐关注的问题。
- 引用的原始资产、报告和外部资料。

普通聚餐、私人提醒和缺少上下文的事件不应默认生成简报。

### 6.4 整理与维护

- 一组记录可能适合建立新 Skill。
- 记录分类或字段可能错误。
- 多条资产可能重复。
- 某个 Goal 长期无数据，建议暂停。
- 报告缺少关键字段。
- 未确认建议需要降级或归档。

这类内容通常进入 Reka 收件箱，不应默认发送系统通知。

## 7. 统一主动候选

### 7.1 为什么统一

不为 Goal、报告、随记升华和会前准备分别建立互不相通的通知系统。所有生成器输出同一份 `RekaCandidate` 契约，再由统一策略决定何时激活和如何送达。

概念结构：

```yaml
id: string
category: commitment | insight | preparation | maintenance
kind: string
title: string
body: string
reason: string
source_refs: []
actions: []
confidence: number
value_score: number
priority: critical | high | normal | low
generated_at: datetime
activate_at: datetime
expires_at: datetime
snooze_until: optional
status: preparing | scheduled | active | resolved | expired
seen_at: optional
resolved_at: optional
outcome: pending | acted | dismissed | snoozed
dedupe_key: string
delivery_policy:
  inbox: boolean
  bubble: boolean
  system_push: boolean
```

### 7.2 生成、激活与失效

内容生成时间和提醒时间必须分离。

例如：

```text
会议时间：周五 14:00
简报生成：周四 14:00
主动激活：会议前 12 小时
失效：会议结束
```

即使简报已经生成，在 `activate_at` 之前也不进入当前主动队列。

有效候选满足：

```text
status = active
outcome = pending
activate_at <= now
expires_at > now
```

`seen_at` 只表达用户是否看过，不改变候选是否仍待处理。用户看过但尚未操作的内容仍可留在收件箱；`acted` / `dismissed`、被新候选取代或到达 `expires_at` 才结束生命周期。`snoozed` 会把候选送回 `scheduled`，等待新的激活时间。

### 7.3 排序

当前主动队列采用：

```text
优先级等级
→ 距离失效时间
→ activate_at
```

不能仅按 `generated_at` 排序，避免低价值报告压住即将失效的会前准备。

### 7.4 去重与预算

- 同一来源、同一目的只保留一个有效候选。
- 新候选可以更新或取代旧候选，不重复轰炸用户。
- 系统通知受每日预算、静默时间和用户偏好约束。
- App 内收件箱可以保留更多内容，但仍需做过期和聚合。
- 用户连续忽略某类候选后，自动增加冷却时间。

## 8. 分发与呈现职责

这些不是三套内容库，而是同一主动事件的不同呈现层。

### 8.1 Reka 即时气泡

职责：回答“刚刚发生了什么？”

- 仅在用户正在使用 App 时出现。
- 一句话为主，短暂展示。
- 最多一个“查看”入口。
- 不承载多步骤确认和长内容。
- 普通即时反馈不要求永久保存。

适合：

- 新记录已计入 Goal。
- Goal 进度更新。
- 记录分类完成。
- Goal 达成后的即时反馈。
- Reka 刚完成某项生成工作。

不适合：

- 多按钮 Goal 创建。
- 长篇报告。
- 必须以后处理的重要提醒。

### 8.2 Reka 收件箱

原 App 内“Reka 通知”建议更名为 **「Reka 收件箱」**。

职责：回答“Reka 为我发现、准备和提醒过什么？”

它是重要主动事件的持久事实来源，支持：

- 未处理。
- 已查看。
- 已完成。
- 已忽略。
- 已过期。

保存内容：

- Goal 建议和提醒历史。
- 报告生成记录。
- 会前简报。
- 随记升华。
- 重要趋势和异常。
- 用户对建议的处理结果。

`dismiss` 不等于删除；历史保留策略需要结合现有 14 天通知窗口重新评估，报告和 Goal 里程碑不应因短通知窗口丢失。

### 8.3 手机系统通知

系统通知只是送达渠道，不产生独立内容。

默认只用于：

- 时间敏感的会议和提醒。
- 已确认 Goal 的最后有效窗口。
- 用户明确订阅的报告。
- 不及时看到会明显失去价值的高优先级事件。

点击后打开对应详情；已读、完成、忽略状态与 Reka 收件箱同步。

### 8.4 内容分配参考

| 内容 | 即时气泡 | Reka 收件箱 | 系统通知 |
|---|---:|---:|---:|
| 新 Goal 建议 | 可轻提示 | 是 | 默认否 |
| Goal 普通进度更新 | 是 | 仅里程碑 | 否 |
| Goal 风险/最后窗口 | App 内可提示 | 是 | 用户允许时 |
| 随记升华总结 | 可提示已生成 | 是 | 默认否 |
| 专业报告 | 可提示已生成 | 是 | 用户订阅时 |
| 会前简报 | App 内提示 | 是 | 通常是 |
| 普通记录处理完成 | 是 | 否 | 否 |
| 重要异常 | 视情况 | 是 | 按时效判断 |

### 8.5 多表面一致性

- 同一候选只有一个 id 和一套状态。
- 任意表面完成、忽略或稍后处理后，其余表面同步。
- `snooze` 更新 `activate_at` 或 `snooze_until`，不创建重复事件。
- 候选过期后操作失效，但历史和来源仍可回看。

> 首页如果未来消费主动队列，也必须复用同一候选和状态。本稿不定义首页展示规则。

## 9. 专业报告模板

通用报告只能回答“记录了什么”，专业模板还需要回答：

```text
发生了什么
→ 有什么变化
→ 为什么值得关注
→ 下一步可以做什么
```

采用三级体系：

1. **通用总结**：记录数量、时间分布、活跃主题和变化。
2. **领域模板**：运动、支出、学习、饮食、睡眠、情绪等领域指标。
3. **Skill 模板**：自定义 Skill 声明自己的指标、准备条件、周期和输出结构。

每个专业模板至少声明：

```yaml
required_metrics: []
readiness_rule: {}
periods: []
sections: []
comparison_baseline: optional
allowed_inferences: []
safety_notes: []
```

医疗、心理和财务领域必须区分：

- 原始事实。
- 统计变化。
- 模型推断。
- 非专业建议。

不得把相关性写成因果，也不得以报告替代专业诊断。

## 10. 用户控制与信任

用户至少可以控制：

- 主动服务总开关。
- Goal 的智能、固定或关闭提醒。
- 专业报告订阅。
- 系统通知权限。
- 免打扰时间。
- 暂停某一 Goal。
- 不再建议某类 Goal 或某类主动内容。
- 查看“为什么收到这条建议”。
- 查看使用了哪些原始数据。

建议和报告必须支持纠错，纠错结果用于：

- 修正 Goal 计入规则。
- 降低错误候选生成器的置信度。
- 调整相似建议的频率。

## 11. 与现有系统的关系

### 11.1 §14 主动 Reka

[§14](../14-proactive-reka.md) 描述的是已实现的 Type A/B、节律、offer 和通知模型。本稿是下一阶段产品模型：

- 将 Type A/B 扩展为四个主动服务领域。
- 将单一 `nudge` 发展为统一 `RekaCandidate`。
- 分离 `generated_at`、`activate_at` 和 `expires_at`。
- 将通知 feed 明确升级为 Reka 收件箱。
- 保留现有置信门、冷却、静默时间和持久化原则。

在实施前，不应直接把 §14 中“已实现”状态改写成新模型已经落地。

### 11.2 习惯 / streak 草案

[design-habit-streak.md](design-habit-streak.md) 中“用户创建习惯对象”的定义已由
[Goal Core](design-goal-core.md) 取代：

- 用户创建由 Assets 自动计算的 Goal。
- Goal Core 首版不实现 Habit 状态。
- capture-fed 自动计入和 streak 反馈仍可复用。
- `completion_event`、里程碑和温柔反馈原则继续有效。

### 11.3 报告系统

[§6](../06-synthesis-report.md) 继续负责报告生成和容器。本稿新增：

- 报告准备条件。
- 主动报告候选。
- 领域模板契约。
- 报告生成、激活和送达时间的分离。

## 12. 非目标

本稿不设计：

- 首页的信息架构、布局、视觉和卡片。
- 通用项目管理或 OKR 系统。
- 无法从记录计算的自由 Goal。
- 完全依赖手工打卡的传统习惯 App。
- Reka 形象、动效和气泡视觉皮肤。
- 具体数据库表、API 和迁移。
- 每个领域最终的专业报告文案。

## 13. 分阶段建议

### Phase 1：Goal Core（已迁出本稿）

Goal 的类型、手动创建、计算、Evidence、不可变规则和实施顺序以
[design-goal-core.md §17](design-goal-core.md#17-实施拆分建议) 为准。本稿不再定义 Goal Phase 1。

### Phase 2：统一主动候选

- 四类候选生成器接口。
- `generated_at` / `activate_at` / `expires_at`。
- 排序、去重、冷却、预算和免打扰。
- Reka 收件箱状态统一。
- 气泡、收件箱和系统通知同步。

### Phase 3：智能发现与准备

- Goal 候选发现。
- 智能机会和最后窗口提醒。
- 习惯状态。
- 随记主题升华。
- 领域 `report_readiness`。
- 会前简报自动生成、激活和失效。

### Phase 4：专业化与自适应

- 专业领域报告模板。
- 跨领域关联候选。
- 根据用户处理结果调整置信度、冷却和送达方式。
- Goal 周期复盘与目标调整建议。

## 14. 成功指标

### Goal

- 有足够记录的用户中，创建或确认至少一个 Goal 的比例。
- Goal 自动计入准确率和用户纠错率。
- Goal 周期完成率。
- Goal 暂停、关闭提醒和删除率。
- Goal 用户的 D7 / D30 留存变化。

### 主动服务

- 候选查看率、处理率和忽略率。
- 每类候选的有效动作转化。
- 系统通知关闭率和退订率。
- 重复、过期或错误建议投诉率。
- 会前简报查看率及会议前查看比例。
- 报告生成后实际阅读和继续行动比例。

### 信任

- “为什么收到”查看率。
- 来源纠错率。
- 同类建议被永久关闭的比例。
- 用户主动调整提醒而非直接关闭的比例。

## 15. 待实施前确认

- Goal DSL 的字段与现有 Skill `render_spec` / schema 如何衔接。

- 习惯状态的周期阈值是否按领域配置。
- Reka 收件箱对不同产物的保留周期。
- 系统通知权限和用户订阅模型。
- 会前简报默认提前量，以及不同会议类型的价值判断。
- 专业报告模板的首批领域及安全审查。
- 首页如何消费主动队列，留待单独设计。
